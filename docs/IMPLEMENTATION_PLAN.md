# Incremental implementation plan

Build from the current `vulnforge/` runtime. Keep the request gate, scope, rate/budget controls, cancellation, redaction, SQLite data, and passing regressions. Work in reviewable slices.

## Stage A — Foundation (PARTIAL)

Implemented: primary CLI entry points, safety profiles, centralized HTTP requester, 15 executing orchestration phases, evidence-linked verified state, additive SQLite schema version, redaction, local lab, baseline regression suite. Scope now supports explicit host/IP/CIDR/port/prefix rules, host/path/parameter exclusions, safe-by-default method allowlists, UTC time windows, and JSON/YAML or IP/CIDR text scope files. State-changing methods require an explicit method policy plus SAFE_ACTIVE, CONTROLLED_ACTIVE, or loopback LAB mode. HTTP methods are checked on each request and redirect hop, embedded URL credentials are denied, DNS checks fail closed for unresolved hosts and mixed public/private answers, and response bodies are streamed under a hard byte ceiling. CLI rate/request overrides cannot exceed the effective safety/resource-profile ceilings, sub-one rates are honored, and Retry-After seconds or HTTP-date values are respected. Dashboard scans now expose safety/resource mode separately from the vulnerability-priority portfolio.

Remaining: project/target objects, genuine checkpoint/resume, fuller test/identity/provenance modeling, and DNS connection pinning against rebinding. The legacy interfaces have been retired; future scope editors must use the canonical policy model.

## Stage B — Discovery and mapping (PARTIAL)

Implemented: target/service observations, robots/sitemap (including bounded sitemap-index traversal), bounded static crawl, endpoint/parameter inventory with evidence references and explicit scope status, response-derived live states, JS static signals with source-exchange links, linked JSON OpenAPI 3.x / Swagger 2.0 declaration parsing, and a typed application/asset model that separates observed pages/endpoints from out-of-scope declarations and unvalidated API operations.

Implemented in this increment: scope-gated fetching of explicitly linked JSON OpenAPI 3.x / Swagger 2.0 documents, bounded operation/parameter/request-response metadata parsing, same-document local references, and declaration-only API inventory. Operations remain `DECLARED_NOT_VALIDATED`; no declared operation is automatically requested.

Next: source-pluggable subdomain/DNS discovery; optional validated reachability checks for JS-derived candidates; richer host/service/port evidence; YAML OpenAPI support only with safe parser/dependency review. JS/API declarations remain inventory leads—not reachable endpoints—until independently observed. Every source must be scope-checked and represented as an observation until validated.

## Stage C — Research workspace (COMPLETE)

Implemented: persisted HTTP exchange history and request/response inspectors; independent request and response IDs; structured JSON Pointer diffs (bounded text diff for non-JSON) in the CLI and dashboard; provenance filtering by module, error state, and parent exchange; and parent-linked Repeater history. The inspector reconstructs prepared requests and parsed responses, not wire captures.

The guarded Repeater requires a stored, completed source scan and its original confirmed scope. Each send requires fresh authorization confirmation, targets the original host/port under the saved scope and method policy, goes through `AuthorizationContext` and `Requester`, is limited to one request at 1 RPS and a 256 KiB response, and does not follow redirects. State-changing methods additionally require an explicit per-send acknowledgement and explicit original method policy under SAFE_ACTIVE, CONTROLLED_ACTIVE, or loopback LAB. Redacted authentication placeholders are rejected; replay is never described as exact when credentials or state are missing. New history remains redacted by default and links back to its source exchange.

Redaction remains the default; loopback-only dashboard scans may explicitly opt in to plaintext sensitive headers/cookies. Differences are observations, not vulnerability verdicts.

## Stage D — Verification engines (COMPLETE for the currently supported set)

Implemented: researcher-configured, read-only two-identity BOLA comparison and paired open-redirect validation can currently emit `VERIFIED` findings. CORS origin-reflection and SQL/parser-error checks are bounded `OBSERVATION_ONLY` checks; they cannot produce confirmed findings. SQL observations consider at most three observed successful in-scope GET query values that are non-sensitive, short, and non-stateful; four GET requests provide baseline and benign-suffix controls plus repeated single-quote probes. The parser diagnostic is a candidate observation only and does not establish altered query semantics, arbitrary SQL execution, or data access. It never uses boolean/timing inference, stacked statements, extraction, writes, or out-of-band callbacks. SQL probe values are redacted and bodies are omitted from persistence. Test cards document rationale, preconditions, steps, negative controls, evidence requirements, stop conditions, method restrictions, and limitations; they are reproducible summaries, not hidden chain-of-thought. Unsupported classes are not executed or represented as findings.

Next: continue one vulnerability class at a time. Each requires a test card, scope-gated execution, positive/negative/adversarial fixtures, an independent verifier, evidence/redaction contracts, and a truthful coverage label before enablement. Do not add broad payload sweeps or autonomous exploitation.

## Stage E — Advanced validation (IN PROGRESS)

First increment: an offline, evidence-linked attack-path component model. Unverified hypotheses become explicitly labeled `HYPOTHESIS` review leads; independently verified findings become `VERIFIED_COMPONENT` records linked to known exchange IDs and finding/test provenance. Each record lists missing evidence and safe next steps. The builder makes no requests, does not join unsupported transitions, and always sets `end_to_end_verified` false. `impact_proven` is true only for the configured BOLA check whose verifier observed unauthorized access to configured sensitive fields; CORS header reflection and redirect destination control explicitly leave impact unproven.

Second increment: a bounded static navigation/workflow map from scope-gated fetched HTML pages, same-scan in-scope endpoint inventory, and markup-declared anchors/forms. Each fetched page is an `OBSERVED_HTTP_VIEW`; anchors are `LINK_DECLARED_NOT_EXECUTED`, and forms are `FORM_DECLARED_NOT_SUBMITTED`. It records evidence exchange IDs and field names only (never submitted field values), limits output size, and excludes targets not known in-scope. No browser is launched, no link or form is executed, and authentication/server-side workflow state stays `UNKNOWN`/`NOT_INFERRED`. Both models are exposed in the report and persisted scan document without a schema migration.

Third increment: offline HAR 1.2 import attaches normalized browser-capture exchanges to an existing completed scan's HTTP history and report. Import requires a fresh explicit CLI authorization acknowledgement plus the scan's original confirmed scope; each URL/method is rechecked against that saved scope using only DNS observations already stored by the scan (no DNS/network request). Out-of-scope, disallowed-method, and excluded-parameter entries are omitted. Bodies are never imported; sensitive headers and URLs are redacted; redirects do not cause navigation. This is HAR ingestion, not browser automation or proxying.

Fourth increment: an optional JSON workflow spec declares source/target/method/expected-status assertions. VulnForge checks those declarations against imported in-scope HAR exchanges and Referer associations only, under the same saved-scope gate. Outcomes are `OBSERVED_EXPECTED_STATUS`, `OBSERVED_UNEXPECTED_STATUS`, `NOT_OBSERVED_IN_CAPTURE`, or blocked/invalid; they never verify a security property, establish that a UI action caused a request, or promote findings. No captured requests are replayed. Capture records and workflow observations are added to the existing exchange store and scan report document without a schema migration.

Fifth increment: explicit `workflow_tests` in the existing auth/config JSON can run bounded read-only HTTP sequences during an explicitly active scan. Planning rejects scripts, per-step credentials/headers, request bodies, state-changing verbs, excluded parameters, and out-of-scope URLs. Each planned GET/HEAD/OPTIONS is rechecked and sent through the existing `Requester`, with budget/rate/stop controls and redirects disabled. HTTP status expectations produce observations only—never vulnerabilities, verified security properties, or impact claims. This is an extensible workflow foundation, not browser JavaScript execution or a general penetration-testing module.

Sixth increment: an optional Playwright browser adapter with human-defined, bounded navigation and selector/URL observation workflows. Browser HTTP is intercepted and delegated through the existing `Requester`; only GET/HEAD/OPTIONS are allowed, each request is scope/rate/budget checked, and WebSockets, downloads, binary assets, and out-of-scope hops are blocked. Browser state is ephemeral; optional storage-state input must be a small owner-only file and is never copied into VulnForge storage. Browser exchange headers are always redacted and bodies omitted, even when other HTTP history is explicitly opted into plaintext. These are navigation observations only—not vulnerability verification, state-changing workflow support, or a security finding.

Still planned: richer browser interaction/capture; authenticated, human-approved stateful workflow execution with independently supported edges; broader vulnerability classes, one verified module at a time; scan comparison, genuine resume, retesting, adaptive budgets, and benchmark metrics. Do not create isolated parallel stores or autonomous exploit chains. The system can expose concise rationale/test cards; private hidden chain-of-thought is not a deliverable.

## Stage F — Hardening (ONGOING)

Run tests, compile checks, loopback CLI smoke, database compatibility tests, request-gate/scope/stop tests, report escaping/redaction, and performance/failure tests after each material change. Do not claim benchmark precision/recall until ground-truth fixtures exist.
