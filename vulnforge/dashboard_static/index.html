SCANNING

New scan

Start with a target you own or are explicitly authorized to assess.

Applied to each in-scope request. Transport-managed headers such as Host and Content-Length cannot be overridden.

The portfolio selects vulnerability priorities; this separate mode controls whether active checks are allowed. LAB is selected with the loopback-only checkbox below.

Only implemented, applicable checks can run. Unsupported classes are reported as unsupported, not simulated.

Advanced: tighten target scope (JSON)

Optional bounds applied in addition to the exact target host: allowed IP/CIDR ranges, ports, URL prefixes, exclusions, methods, and time window. Methods default to GET, HEAD, and OPTIONS. State-changing methods require SAFE_ACTIVE, CONTROLLED_ACTIVE, or loopback LAB mode. This does not add batch targets.

Advanced: configure the supported read-only BOLA check

Optional JSON for a same-origin, three-GET owner/non-owner comparison. Use only test identities and a system you are authorized to assess. Choose Critical, High, or Full below and explicitly choose SAFE_ACTIVE or CONTROLLED_ACTIVE; other vulnerability classes remain unsupported.

Verification requires distinct identities, an owner baseline, a repeatable non-owner read, and the configured sensitive field.

Sensitive history is readable by anyone with access to this database. This option is accepted only when the dashboard binds to localhost.

Testing safety

Use a staging target where possible. Requests remain subject to authorization, scope, rate, request-budget, response-size, and redirect controls.
